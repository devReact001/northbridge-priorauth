# Integrations: FHIR and MCP (Week 4)

## Why MCP here

The chart lookup and the outbound send could be plain function calls. They are MCP servers because that is how a
real deployment would expose them: one server per system, with a typed tool list that any MCP client can use,
including Claude Desktop, MCP Inspector, or another agent. Swapping the synthetic data for a hospital's FHIR
endpoint changes one setting, not the agent.

## The FHIR server (`northbridge-fhir`, read only)

```
python -m app.mcp_servers.fhir_server        # stdio transport, run from the backend folder
```

| Tool | Returns |
|---|---|
| `get_patient` | Sex, birth date, identifier. No name or address (minimum necessary) |
| `get_conditions` | Problem list with ICD-10 codes and onset dates |
| `get_medications` | Medication orders with dose, prescriber, date and status |
| `get_procedures` | Therapies and procedures (physical therapy, injections) with dates, performer and outcome |
| `get_exam_findings` | Recorded physical examination findings |
| `get_imaging_reports` | Radiology reports with dates and conclusions (prior imaging of the same body part) |
| `get_service_requests` | Orders with CPT codes and the reason for each |

Every tool takes only `patient` (the identifier on the request) and returns at most 25 facts, newest first. A fact is one line of text built by code from one FHIR
resource, for example:

```
Procedure/proc-1 (2026-02-16 to 2026-03-30): Physical therapy, twice weekly, by S. Kulkarni (PT, DPT), status completed. Outcome: Pain with stairs unchanged after 6 weeks of therapy.
```

Data sources (`FHIR_SOURCE`): `bundle` reads the synthetic FHIR R4 bundles in `backend/app/data/fhir/`
(generated by `scripts/make_fhir_fixtures.py`); `http` calls a FHIR REST API at `FHIR_BASE_URL` with standard
search parameters (`Patient?identifier=`, `Condition?patient=`, `Observation?patient=&category=exam`).
Use only synthetic data with a public test server.

## The outbound server (`northbridge-outbound`, write side)

```
python -m app.mcp_servers.outbound_server
```

| Tool | Effect |
|---|---|
| `submit_prior_authorization` | Writes a FHIR `Claim` (`use: preauthorization`) with the approved letter to the outbox |
| `send_clinician_message` | Writes an approved information request to the outbox |

The outbox (`OUTBOX_DIR`, default `outbox/` in the project root) stands in for a payer portal and a clinician
inbox. Both tools require `approved_by`, validate their input, reject unsafe case ids, and are idempotent: the
second call for the same case returns `duplicate` and sends nothing.

## Fixtures and what each is for

| Patient | Note | What the chart adds |
|---|---|---|
| SYN-01203 | `note_03_knee_meets` | Corroborates the note. Result should not change. |
| SYN-00417 | `note_01_mri_lumbar` | Corroborates the note. |
| SYN-00982 | `note_02_incomplete` | The thin note is missing the radiograph, therapy, exam and order. The chart has all of those. Locking or catching is recorded nowhere, so one real gap remains and the request to the clinician shrinks to that item. |
| SYN-04471 | `note_06_knee_repeat_mri` | The note looks complete, but the chart shows an MRI of the same knee on 2026-01-14. The policy excludes a repeat MRI within 12 months without a change in clinical status, so a human must decide. |
| SYN-02218, SYN-03377 | `note_04`, `note_05` | Consistent with their notes. |

## Try the servers without the workflow

```
cd backend
npx @modelcontextprotocol/inspector python -m app.mcp_servers.fhir_server
```

MCP Inspector opens a page where you can list the tools and call them by hand.

## Security notes worth stating in an interview

- **Read and write are separate servers.** A client can be given the read-only one alone.
- **No free-form query tool.** The agent can only call the seven fixed tools, so there is nothing to inject a
  query into.
- **No filter parameters.** An earlier version let the agent pass `since` and `contains`; on a real run it filtered
  with keywords like "knee" and hid the therapy record and most exam findings from itself. Tools now take only the
  patient, so the agent cannot narrow away evidence.
- **The patient is fixed by code.** The identifier passed to every tool is overwritten with the one on the request,
  and an attempt to use another is recorded in the audit trail.
- **Chart text is untrusted data.** It reaches the model inside tagged blocks with instructions to ignore any
  instructions inside them, and it can only affect the outcome as verified quotes, which a human reads.
- **Minimum necessary.** No names, addresses or free-text notes beyond the fields a requirement needs.
- **Writes need a person.** The `dispatch` step is unreachable except through `human_review`, and every write
  carries the approver's name.
- **Failure is safe.** If the FHIR server is down, the case continues on the note alone and says so.
